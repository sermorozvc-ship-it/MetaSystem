# Тренировочный дневник — автосохранение подходов

Этот файл — обязательный чек-лист и набор правил для любых изменений
в логике тренировочного дневника. Проверять перед каждым пушем.

## Контекст

Главный компонент: `src/app/programs/[programId]/page.tsx`
Сервис записи: `src/lib/services/training.ts` → `upsertTrainingEntry`
Таблица БД: `training_entries` (UNIQUE(program_id, day_number))

История проблемы (повторяющаяся, поэтому в steering):

- Кнопка «Сохранить» зависала после первого нажатия — `isSaving=true` не
  сбрасывался при подвисшей сети/RLS, потому что не было таймаута на upsert.
- Подходы не сохранялись автоматически — клиент думал, что нажал «Сохранить»,
  а на деле параллельный автосейв перетирал состояние, и при перезагрузке
  всё слетало.

## Контракт автосохранения

### 1. `upsertTrainingEntry` ДОЛЖЕН проходить через `withTimeout`

В `src/lib/services/training.ts` есть утилита `withTimeout`. Все операции
тренировочного дневника, которые блокируют UX (upsert записи, complete day),
оборачиваются в неё. Без таймаута promise может «висеть» бесконечно и
залочить кнопки UI.

```ts
const { data, error } = await withTimeout(
  supabase.from('training_entries').upsert(...).select().single(),
  'upsertTrainingEntry',
)
```

При добавлении новых сетевых операций, влияющих на ввод подходов, —
оборачивать в `withTimeout` обязательно.

### 2. `saveEntry` использует mutex `inFlightRef` + очередь `pendingRef`

В `programs/[programId]/page.tsx`:

- `inFlightRef` — флаг «прямо сейчас идёт upsert». Параллельные вызовы запрещены.
- `pendingRef` — флаг «во время текущего upsert'а пришли новые правки,
  после завершения нужно сохранить ещё раз».
- `setIsSaving(false)` и `inFlightRef.current = false` ВСЕГДА вызываются в `finally`.

Любые новые точки сохранения (например, кастомные «сохранить блок X»)
ОБЯЗАНЫ проверять `inFlightRef.current` перед стартом и обновлять его.

### 3. Дебаунс автосохранения = 800мс

Это согласовано с `CheckinBlock`. Не увеличивать без серьёзной причины:
длинный дебаунс провоцирует гонку «ручной save vs auto-save».

Таймер хранится в `debounceTimerRef`, при `handleCompleteDay` /
`handleSaveCompleted` принудительно очищается, чтобы не записать дважды.

### 4. Локальный бэкап в localStorage

Ключ: `training_draft_<programId>_<dayNumber>`

Пишется ПЕРЕД отправкой в Supabase (внутри дебаунс-эффекта и в
`beforeunload`-обработчике). Снимается из бэкапа в `handleCompleteDay`
при успешном завершении дня.

При загрузке записи дня:
1. Запрашиваем `training_entries` из БД.
2. Если локальный черновик новее, чем `updated_at` сервера на 1с+ —
   восстанавливаем из черновика и помечаем `userChangedRef.current = true`,
   чтобы автосейв досохранил его.
3. Если сервер ответил ошибкой, но есть черновик — используем черновик
   и показываем `saveStatus='error'` с пояснением.

### 5. UI-индикатор `saveStatus`

Состояния: `idle | saving | saved | error`. Показывается над кнопками
«Сохранить» / «Завершить». Это снимает у пользователя ощущение
«нажал и ничего не понятно».

При смене дня сбрасываем в `idle` и чистим дебаунс-таймер.

### 6. Защита от «вечного спиннера» при заморозке вкладки / смене сети

Сценарий, который НЕ ловился `withTimeout`: на телефоне экран гаснет
между подходами → браузер замораживает вкладку → `setTimeout` внутри
`withTimeout` НЕ тикает. Если в этот момент рвётся сеть (особенно при
переключении VPN — актуально для РФ), upsert умирает молча, а лок
`inFlightRef` и спиннер `isSaving` остаются «висеть». Раньше чинилось
только hard reload.

Две гарантии:

- **`lockIsFree()` со стейл-таймстампом `inFlightSinceRef`.** Лок старше
  `STALE_LOCK_MS` (15с — чуть больше сетевого таймаута 12с) считается
  протухшим и принудительно снимается. КРИТИЧНО: при снятии протухшего
  лока `lockIsFree` сбрасывает И `inFlightRef`, И визуальный спиннер
  (`setIsSaving(false)` + `saveStatus → idle`). Сброс только ref'а
  оставлял бы кнопку `disabled` навсегда.

- **Watchdog-эффект на `visibilitychange` / `focus` / `online`.** При
  возврате вкладки или восстановлении сети: (1) снимает залипший лок
  через `lockIsFree()`; (2) если остались несохранённые правки
  (`userChangedRef.current` и `lastServerEntryRef.current !== null`) —
  тихо досохраняет их (`saveEntryRef.current?.(true)`). Это и есть
  «раз и навсегда»: даже молча оборванный запрос не оставляет
  залипшую кнопку, а данные дотягиваются сами.

`STALE_LOCK_MS` держать чуть выше сетевого таймаута `withTimeout` (12с).
Если поднимать `withTimeout` — поднимать и `STALE_LOCK_MS`.

## Чек-лист перед пушем (обязательный)

При любых изменениях в `programs/[programId]/page.tsx`,
`src/lib/services/training.ts` или связанной логике:

- [ ] `upsertTrainingEntry` оборачивает запрос в `withTimeout`.
- [ ] В `saveEntry` есть `inFlightRef` + `pendingRef` + `try/finally`.
- [ ] `setIsSaving(false)` вызывается в `finally`, не только в `try`.
- [ ] Дебаунс-эффект пишет в `localStorage` ДО запуска таймера upsert.
- [ ] При смене дня `debounceTimerRef` чистится, `saveStatus` сбрасывается в `idle`.
- [ ] `handleCompleteDay` чистит `localStorage`-черновик после успешного завершения.
- [ ] `handleCompleteDay` и `handleSaveCompleted` уважают `inFlightRef`
      (не запускаются параллельно с автосейвом).
- [ ] Ручной тест: ввести вес → подождать 1с → должно появиться
      «✓ Сохранено автоматически».
- [ ] Ручной тест: ввести вес → нажать «Сохранить» 3 раза подряд →
      кнопка не должна остаться `disabled` навсегда.
- [ ] Ручной тест: ввести вес → жёстко перезагрузить (Ctrl+Shift+R)
      ДО появления «✓ Сохранено» → данные должны восстановиться из
      localStorage и сохраниться сами в течение секунды.
- [ ] Ручной тест: открыть DevTools → Network → throttle Offline →
      ввести вес → через 12с увидеть «⚠ ... timeout», кнопка снова
      кликабельна.
- [ ] `lockIsFree()` при снятии протухшего лока сбрасывает И спиннер
      (`setIsSaving(false)` + `saveStatus`), а не только `inFlightRef`.
- [ ] Есть watchdog-эффект на `visibilitychange`/`focus`/`online`,
      который снимает залипший лок и досохраняет правки при возврате.
- [ ] `STALE_LOCK_MS` (15с) > сетевого таймаута `withTimeout` (12с).
- [ ] Ручной тест (телефон): ввести вес → погасить экран на ~30с →
      разблокировать → спиннер не должен висеть, данные досохранены.
- [ ] Ручной тест: ввести вес → переключить VPN (сменить IP) →
      вернуться во вкладку → кнопка кликабельна, данные на месте.

## Чего НЕ делать

- Не возвращать дебаунс к 1500мс+ — это провоцирует гонки.
- Не убирать `withTimeout` ради «чистоты».
- Не делать `await upsertTrainingEntry(...)` без try/catch — иначе один
  отвалившийся запрос залочит UI.
- Не пытаться слать несколько upsert параллельно для одного `(program, day)` —
  Postgres сериализует через UNIQUE-индекс, но в UI это создаёт мерцание
  и потерю последних правок.
- Не «оптимизировать» `latestDataRef` — он специально сделан как ref,
  чтобы saveEntry читал свежие значения без пересоздания колбэка.
