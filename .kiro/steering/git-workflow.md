# Git workflow в этом проекте

Личный проект одного разработчика. Работаем напрямую в `main` — без
feature-веток и PR-ов под каждый коммит.

## Правило

Когда пользователь говорит «пуш» / «коммит пуш» / «запушь»:

1. `git add` нужных файлов (не `.` оптом, чтобы не подцепить мусор).
2. `git commit -m "<conventional message>"` — стиль как в существующих
   коммитах: `fix(...)`, `feat(...)`, `docs(...)`, `chore(...)`.
3. `git push origin main` — напрямую, без ветки.

Никаких `git checkout -b`, никаких `gh pr create` / `mcp_github_create_pull_request`,
никаких `mcp_github_merge_pull_request`. Это создаёт двойной билд на
Vercel (preview + prod) и просто шум.

## Когда всё-таки делать ветку + PR

Только если пользователь явно попросил:
- «сделай PR»
- «через ветку»
- «не пуши сразу в прод»
- меняем что-то рискованное и я сам предложил подстраховаться, а
  пользователь согласился

В остальных случаях — `main` напрямую.

## Стиль коммит-сообщений

Смотрим `git log --oneline -10` перед коммитом. Текущий стиль:

```
fix(parser): убран жадный сбор '## Сводка' в Резюме тренера
fix(programs): убран дубль блока prevWeekStats + enrich дозаполняет недостающие поля
feat(programs): UI «Сводка прошлой недели» + расширенный парсер
docs(training-brain): сообщение об ошибке GITHUB_TOKEN + инструкция по Vercel
fix(desktop): таймауты на чтение + UI fallback на вечном спиннере
```

- Тип: `fix` / `feat` / `docs` / `chore` / `refactor`.
- Скоуп в скобках: модуль или фича (`programs`, `auth`, `parser`, `desktop`).
- Сообщение на русском, кратко по сути.
- Если у изменения несколько аспектов — основное в `-m`, детали в
  дополнительных `-m` (или body).

## Безопасность

Push безопасен потому что:
- Vercel ловит ошибки сборки на стадии build и не выкатывает поломанный код.
- `tsc --noEmit` прогоняем перед коммитом, если меняли TS.
- Откат всегда можно сделать через Vercel «Promote previous deployment»
  или `git revert <sha> && git push`.

Что ВСЁ ЕЩЁ требует подтверждения у пользователя:
- удаление файлов / папок;
- миграции БД (`mcp_supabase_apply_migration`);
- `.env*` правки;
- что-то трогающее платежи, авторизацию или RLS-политики, если изменения
  обширные и не из явного запроса пользователя.
