# Десктоп: страницы не грузятся без принудительной перезагрузки

Повторяющаяся проблема: на десктопе страницы зависают на лоадере или
показывают пустой экран до Ctrl+F5. На мобилке не воспроизводится
(там реже несколько вкладок и меньше JS-чанков на ход).

## Корни проблемы (исторически)

1. **Слишком короткий `timeout` страховки в `AuthContext`** (был 1500мс).
   На холодном старте десктопа `getSession()` иногда резолвится дольше,
   и страховка форсит `isLoading=false` с `user=null`. Дальше срабатывает
   guard `if (!authLoading && !user) → редирект`, и пользователь получает
   редирект поверх валидной сессии.

2. **`window.location.href = '/auth'` в guard-ах** делает full page
   reload вместо мягкого редиректа. На десктопе с большими чанками это
   ощущается как «страница не загрузилась». На мобилке чанки меньше →
   меньше заметно.

3. **Сессия не обновляется при возврате к вкладке.** Десктоп часто
   держит вкладку «спящей»; access_token истекает в фоне, supabase не
   успевает обновить — навигация виснет на RLS-запросах.

4. **Race condition в Web Locks API + Supabase Auth** при нескольких
   вкладках (десктоп) — `reactStrictMode: false` уже стоит ради этого,
   плюс кастомный `inTabLock` в `lib/supabase/client.ts`.

## Текущие гарантии (НЕ откатывать)

В `src/lib/auth/AuthContext.tsx`:

- Таймаут страховки = **5000мс** (не 1500мс — короткий триггерил ложный
  редирект на /auth при медленном getSession).
- Слушаем `visibilitychange` + `focus` → принудительный `getSession()`,
  чтобы при возврате к вкладке access_token обновился через
  `onAuthStateChange`.
- `globalSession` / `globalUser` / `globalResolved` переживают ремаунт
  компонента при client-side навигации — без них каждая страница делала
  бы новый `getSession()`, и снова попадали в гонку.

В `src/lib/supabase/client.ts`:

- `inTabLock` сериализует Auth-операции внутри вкладки, но НЕ блокирует
  между вкладками (иначе deadlock на десктопе).
- `safeGetUser` имеет таймаут 4с и держит кеш на 10с — чтобы не делать
  параллельных getUser из разных компонентов.

В страницах (guard-эффекты):

- НЕ использовать `window.location.href = '/auth'` для guard-редиректа.
  Только `router.replace('/auth')`. `window.location` — тяжёлый full
  reload, оправдан ТОЛЬКО для:
  - переходов на ЮMoney (внешний URL);
  - signOut (нужно сбросить всё SPA-состояние);
  - return-from-payment (нужно перечитать профиль с сервера).

## Чек-лист перед пушем

- [ ] В `AuthContext.tsx` таймаут страховки >= 5000мс.
- [ ] В `AuthContext.tsx` есть слушатели `visibilitychange` и `focus`.
- [ ] В `lib/supabase/client.ts` присутствует `inTabLock`, передан в
      `createBrowserClient` через `auth.lock`.
- [ ] В `next.config.js` `reactStrictMode: false`.
- [ ] Новые страницы используют `router.replace('/auth')`, а НЕ
      `window.location.href = '/auth'` для auth-guard.
- [ ] Ручной тест на десктопе: открыть 3+ вкладки приложения →
      переключаться между ними → каждая страница должна грузиться
      без принудительной перезагрузки.
- [ ] Ручной тест на десктопе: оставить вкладку висеть 10+ минут →
      вернуться → не должно быть «зависших» лоадеров; данные
      обновляются автоматически.
- [ ] Ручной тест: hard reload (Ctrl+Shift+R) на любой защищённой
      странице — должна загрузиться за 1-2 секунды без редиректа на /auth.

## Если проблема снова всплывёт

1. Проверить console: есть ли `[Auth] Timeout — forcing isLoading=false`.
   Если есть — значит первичный `getSession` опять подвисает. Увеличить
   таймаут не всегда правильно: проверить, не поломан ли `inTabLock`,
   не вернулся ли где-то `disableLocks: true` в `createBrowserClient`.
2. Проверить Network tab: есть ли запросы к Supabase, которые не
   завершаются. Если да — проблема на стороне `withTimeout` в
   `services/training.ts` (или аналогичных) — нужен таймаут.
3. Проверить, не появились ли новые `window.location.href` в guard-ах —
   пройтись `grep_search`-ом.
